# ADR 0001：使用轻量 OpenWrt CI 控制仓库

## 状态

已接受

## 背景

本项目需要构建 OpenWrt 官方 `openwrt-25.12` 分支的 x86_64 软路由固件。项目目标不是维护 OpenWrt 源码分支，而是稳定、可重复地描述固件配置并通过 GitHub Actions 产出镜像。

如果把 OpenWrt 源码、构建输出或大量本地脚本提交到本仓库，仓库会快速膨胀，后续维护者也更难判断哪些文件是真正的项目输入。另一方面，完全依赖默认配置又会导致“构建成功但功能缺失”的风险。

## 决策

本项目采用轻量 GitHub Actions 控制仓库模式：

- 只维护 x86_64 软路由目标，不引入多目标矩阵。
- 只维护一份固件配置。
- 在 GitHub Actions 中拉取 OpenWrt 官方源码。
- 当前阶段只通过 GitHub Actions Artifacts 交付固件产物。
- 只预装 banIP 等安全能力，不内置第三方规则源或私有策略。
- 对构建配置和固件 manifest 做显式校验，避免缺包固件被当作成功产物。

## 后果

正面影响：

- 仓库保持小而清晰，主要文件都是构建输入或项目约束。
- 构建过程更接近官方 OpenWrt 源码状态，减少本地源码副本带来的偏差。
- 单配置减少缓存分裂和排错复杂度。
- Artifacts 交付适合当前配置仍在调整的阶段。
- Manifest 校验能阻止缺少关键运行时包的固件进入交付结果。

负面影响：

- 暂不支持 ARM、其他 x86 profile 或多个固件版本并行产出。
- 需要依赖 GitHub Actions 的运行环境、缓存和 artifact 保留策略。
- 当配置稳定后，如果需要长期分发，还需要补充 GitHub Release 流程。

## 备选方案

备选方案一：提交 OpenWrt 源码或使用子模块。

该方案能让源码版本在仓库层面更显式，但会显著增加仓库体积和维护成本，也偏离本项目作为控制仓库的定位。

备选方案二：使用多配置或多目标矩阵。

该方案更灵活，但会扩大缓存、构建时间和故障面。当前只有 x86_64 软路由需求，矩阵化还没有足够收益。

备选方案三：直接发布 GitHub Release。

该方案更适合稳定版本分发，但当前配置仍在迭代，先使用 Artifacts 更利于验证和调整。
